# account-audit-logging Specification

## Purpose
Centralized, server-side, append-only audit logging for AquaSense. Every important account or system action must produce an auditable activity record that identifies the authenticated account or system actor, timestamp, action, target/resource, result, and relevant contextual metadata. Audit records must be generated and persisted server-side and must not depend solely on Flutter local storage. The audit history is append-oriented and tamper-resistant/immutable where practical.

## Requirements

### Requirement: Unified audit event structure
The system SHALL define a single, domain-agnostic audit event structure with the following mandatory fields:

- `eventId`: Unique, immutable identifier for the audit record (generated by the backend).
- `timestamp`: Server-side timestamp of the event (ISO 8601 with timezone).
- `actor`: Actor identity that initiated or caused the action.
  - For human actions: `type: user`, `id: <authenticatedUserId>`, `displayName: <display name>`.
  - For automatic operations: `type: system`, `id: <explicitAutomationId>` (e.g., `auto-awd`, `config-sync`, `node-provisioner`), `displayName: <automation label>`.
  - For emergency or override actions: `type: emergencyOverride`, `id: <authenticatedUserId>`, `displayName: <display name>`.
- `category`: Enumerated category of the event (e.g., `authentication`, `authorization`, `field-config`, `node-management`, `sensor-config`, `irrigation`, `security`).
- `action`: Human-readable or machine-action name describing the operation (e.g., `user.login`, `node.register`, `irrigation.start`, `field.config.update`).
- `target`: Target/resource identifier for the action.
  - `type`: Resource type (e.g., `user`, `field`, `node`, `sensor`, `irrigation-system`, `settings`, `gateway`).
  - `id`: Unique identifier of the target.
  - `displayName`: Optional human-readable label for the target.
- `result`: Outcome of the action (`success`, `failed`, `denied`, `partial`).
- `metadata`: Contextual metadata relevant to the event (e.g., correlation IDs, IP address, request ID, prior state, new state, rationale, failure reason).

#### Scenario: Successful user login
- **WHEN** an authenticated user logs in successfully
- **THEN** the system creates an audit event with `actor.type: user`, `category: authentication`, `action: user.login`, `result: success`, and metadata containing the request ID and source IP

#### Scenario: Failed login with invalid credentials
- **WHEN** an authentication attempt fails due to invalid credentials
- **THEN** the system creates an audit event with `actor.type: user`, `category: authentication`, `action: user.login`, `result: failed`, and metadata containing the failure reason and source IP

### Requirement: Audit event categories
The system SHALL categorize audit events into the following categories, and each category SHALL have a defined set of actions:

- `authentication`: login, logout, token refresh, session expiration, failed authentication attempts
- `authorization`: permission checks, role changes, access denials, permission grants
- `field-config`: field creation, field updates, field deletion, field assignment changes
- `node-management`: node registration, node removal, node reassignment, node replacement, node decommissioning
- `sensor-config`: sensor configuration changes, calibration changes, interval changes
- `irrigation`: manual irrigation commands, automatic irrigation events, irrigation configuration changes
- `security`: security-sensitive operations, policy changes, security configuration changes
- `system`: system-level events, maintenance, backups, and other infrastructure events

#### Scenario: User changes field configuration
- **WHEN** an authenticated user updates a field's soil type or crop stage
- **THEN** the system creates an audit event with `category: field-config`, `action: field.config.update`, and metadata containing the previous and new values

#### Scenario: Node is reassigned to a new zone
- **WHEN** an authorized operator reassigns a sensor node to a different zone
- **THEN** the system creates an audit event with `category: node-management`, `action: node.reassign`, and metadata containing the previous and new zone IDs

### Requirement: Explicit actor identity for human and system actions
The system SHALL identify the authenticated account or system actor that initiated every important account or system action.

- Human actions SHALL use `actor.type: user` with the authenticated user's ID and display name.
- Automatic operations SHALL use `actor.type: system` with an explicit automation identifier (e.g., `auto-awd`, `config-sync`).
- Emergency or override actions SHALL use `actor.type: emergencyOverride` with the authenticated user's ID and display name.
- The system SHALL NOT allow automatic operations to pretend to be human accounts.

#### Scenario: Automatic irrigation triggers a pump
- **WHEN** the automatic irrigation supervisor triggers a pump start
- **THEN** the audit event SHALL have `actor.type: system`, `actor.id: auto-awd`, and `action: irrigation.start`

#### Scenario: Human operator manually starts irrigation
- **WHEN** an authenticated operator manually starts irrigation
- **THEN** the audit event SHALL have `actor.type: user`, `actor.id: <userId>`, and `action: irrigation.start`

### Requirement: Target and resource identification
The system SHALL identify the target/resource for every audit event using a structured target object.

- The target SHALL include a `type` (resource category), `id` (unique identifier), and optional `displayName`.
- For actions affecting multiple resources (e.g., bulk updates), the target SHALL include a `list` of target objects or a `count` field.
- For actions affecting no specific resource (e.g., global configuration changes), the target SHALL use a stable pseudo-ID (e.g., `global`) with a descriptive type.

#### Scenario: User changes irrigation configuration for a field
- **WHEN** an authenticated user updates irrigation settings for a specific field
- **THEN** the audit event SHALL have `target.type: field`, `target.id: <fieldId>`, and metadata containing the old and new irrigation configuration

#### Scenario: System performs global configuration sync
- **WHEN** an automatic system process updates global configuration
- **THEN** the audit event SHALL have `target.type: global`, `target.id: global`, and `actor.type: system`

### Requirement: Result and status tracking
The system SHALL record the result/status of every audit event.

- `success`: The action completed successfully.
- `failed`: The action was attempted but failed (with failure reason in metadata).
- `denied`: The action was denied due to authorization or policy.
- `partial`: The action partially completed (some resources updated, others failed).

#### Scenario: User attempts unauthorized node decommissioning
- **WHEN** an authenticated user without permission attempts to decommission a node
- **THEN** the system SHALL create an audit event with `result: denied`, `category: authorization`, and metadata containing the reason for denial

#### Scenario: Bulk node replacement partially fails
- **WHEN** a bulk node replacement operation partially fails
- **THEN** the system SHALL create an audit event with `result: partial`, `category: node-management`, and metadata containing the failed and successful target IDs

### Requirement: Contextual metadata
The system SHALL capture relevant contextual metadata for every audit event.

- Metadata SHALL include a `correlationId` for linking related events across the system.
- Metadata SHALL include a `requestId` for tracing individual API calls.
- Metadata SHALL include the client IP address or device identifier where available.
- Metadata SHALL include the prior state and new state for configuration changes.
- Metadata SHALL include the failure reason for failed or denied events.
- Metadata SHALL include the rationale or reason for override actions.

#### Scenario: User changes node transmission interval
- **WHEN** an authorized operator updates a node's transmission interval
- **THEN** the audit event SHALL have metadata containing the previous interval, new interval, and the operator's rationale

#### Scenario: User overrides automatic irrigation
- **WHEN** an authenticated operator overrides an automatic irrigation cycle
- **THEN** the audit event SHALL have metadata containing the override reason and the current irrigation state

### Requirement: Server-side generation and persistence
The system SHALL generate audit events server-side for every important account or system action.

- Audit events SHALL NOT depend solely on Flutter local storage.
- Audit events SHALL be persisted in a backend-managed audit log store.
- Audit events SHALL be generated even when the client is offline (if the backend can determine the action was attempted).
- Audit events SHALL be generated for both successful and failed operations.

#### Scenario: User attempts irrigation command while offline
- **WHEN** an authenticated user attempts to start irrigation while the mobile app is offline
- **THEN** the system SHALL log the attempted action server-side if the request reaches the backend (e.g., via queued request) or record a client-side pending audit marker that is resolved once the request is processed

#### Scenario: Backend logs successful node registration
- **WHEN** the backend receives a node registration request and successfully registers the node
- **THEN** the system SHALL create an audit event with `result: success` and metadata containing the node ID, MAC address, and registering user ID

### Requirement: Append-oriented and tamper-resistant audit history
The system SHALL design the audit history as append-oriented and tamper-resistant/immutable where practical.

- Audit records SHALL be immutable after creation (no update or delete operations on individual records).
- Audit records SHALL be stored in an append-only table or log structure.
- Audit records SHALL be ordered by timestamp and/or sequence number.
- The system SHALL support batch-level integrity verification (e.g., hash-chaining, digital signatures, or equivalent) where practical.
- The system SHALL support retention policies and archival strategies for audit records.

#### Scenario: Audit record integrity verification
- **WHEN** an administrator verifies the audit history
- **THEN** the system SHALL be able to verify the integrity of the audit log batch using hash-chaining or equivalent mechanisms

#### Scenario: Audit record retention
- **WHEN** the audit retention period expires for a record
- **THEN** the system SHALL archive or purge the record according to the configured retention policy, preserving evidence of the deletion action

### Requirement: Retention considerations
The system SHALL define and enforce audit record retention policies.

- Audit records SHALL be retained for a configurable period (default: 1 year).
- The retention period SHALL be configurable per environment (development, staging, production).
- Records SHALL be archived or purged according to the retention policy.
- The system SHALL log the archival or purge action as an audit event.

#### Scenario: Audit record retention expires
- **WHEN** the retention period expires for an audit record
- **THEN** the system SHALL archive the record to cold storage or purge it according to the configured retention policy, and SHALL create an audit event for the archival or purge action

### Requirement: Access restrictions
The system SHALL restrict access to audit history based on role-based access control.

- Only users with `admin` or `fieldAdmin` roles SHALL be able to view the full audit history.
- Users with `auditor` role (if defined) SHALL be able to view the audit history with read-only access.
- Users with `operator` or `viewer` roles SHALL NOT be able to view the full audit history.
- The audit history UI SHALL be restricted to authorized roles only.
- The audit history API SHALL enforce role-based access control.

#### Scenario: Viewer attempts to view audit history
- **WHEN** an authenticated user with `viewer` role attempts to access the audit history
- **THEN** the system SHALL deny access with a `403 Forbidden` response and SHALL create an audit event with `result: denied` and `category: authorization`

#### Scenario: Admin views audit history
- **WHEN** an authenticated user with `admin` role accesses the audit history
- **THEN** the system SHALL present the audit history UI with filtered, paginated results

### Requirement: Failed operation handling
The system SHALL audit failed operations, including authorization denials and validation errors.

- Failed operations SHALL create audit events with `result: failed` or `result: denied`.
- Failed operations SHALL include the failure reason in metadata.
- Authorization denials SHALL be audited to support security investigations.
- Failed operations SHALL NOT create misleading success events.

#### Scenario: User attempts to update irrigation config without permission
- **WHEN** an authenticated user without irrigation configuration permission attempts to update irrigation settings
- **THEN** the system SHALL create an audit event with `result: denied`, `category: authorization`, and metadata containing the denial reason

### Requirement: Backend API for audit history viewing
The system SHALL provide REST API endpoints for viewing the audit history.

- `GET /api/audit/events`: Fetch a paginated list of audit events with filters.
- `GET /api/audit/events/{eventId}`: Fetch a single audit event by ID.
- `POST /api/audit/events`: Internal endpoint for backend-generated audit events (not exposed to frontend clients).
- The API SHALL support filtering by category, actor, target, time range, and result.
- The API SHALL support pagination (limit and offset or cursor-based).

#### Scenario: Fetch audit history
- **WHEN** an authorized user requests the audit history
- **THEN** the system SHALL return a paginated list of audit events filtered by the requested criteria

#### Scenario: Fetch single audit event
- **WHEN** an authorized user requests a specific audit event
- **THEN** the system SHALL return the single audit event by ID

### Requirement: UI for authorized audit history viewing
The system SHALL provide a UI for authorized users to view the audit history.

- The UI SHALL be accessible from the Settings or Admin section.
- The UI SHALL support filtering by category, actor, target, time range, and result.
- The UI SHALL support pagination or infinite scrolling for large audit histories.
- The UI SHALL display event summary information (timestamp, actor, action, target, result).
- The UI SHALL allow viewing full event details including metadata.
- The UI SHALL be restricted to authorized roles only.

#### Scenario: Admin views audit history
- **WHEN** an authorized user opens the audit history UI
- **THEN** the system SHALL present the audit history with filters and paginated results

#### Scenario: User views audit event details
- **WHEN** an authorized user selects an audit event from the list
- **THEN** the system SHALL display the full event details including metadata

### Requirement: Real-time audit event streaming
The system SHALL support real-time delivery of audit events through the existing real-time transport.

- The backend SHALL publish `auditEvent` events to the real-time channel.
- The frontend SHALL subscribe to `auditEvent` events through the `RealtimeCoordinator`.
- The frontend SHALL validate audit event payloads before rendering them.
- The frontend SHALL update the audit history UI in real time when new events are received.

#### Scenario: Real-time audit event received
- **WHEN** the backend publishes a new audit event
- **THEN** the frontend SHALL receive the event through the real-time channel and update the audit history UI

### Requirement: Backward compatibility with irrigation audit logs
The system SHALL maintain backward compatibility with existing irrigation audit log endpoints and models.

- Existing `IrrigationExecutionAuditLog` models SHALL be compatible with the unified `AccountAuditEvent` schema.
- Existing `/api/irrigation/audit-log` endpoint SHALL continue to work.
- The unified `/api/audit/events` endpoint SHALL be able to return irrigation audit events.
- The frontend SHALL be able to migrate from irrigation-specific audit logs to the unified audit history.

#### Scenario: Existing irrigation audit log is fetched
- **WHEN** an authorized user fetches the irrigation audit log
- **THEN** the system SHALL return irrigation audit events in the same format as before

#### Scenario: Unified audit history includes irrigation events
- **WHEN** an authorized user fetches the unified audit history
- **THEN** the system SHALL include irrigation audit events in the results

### Requirement: Security-sensitive operation coverage
The system SHALL audit all security-sensitive operations, including but not limited to:

- Authentication events (login, logout, token refresh, failed login attempts)
- Authorization decisions (grants, denials, role changes)
- Field configuration changes
- Sensor-node registration/removal/reassignment
- Sensor configuration changes
- Manual irrigation commands
- Automatic irrigation events
- Security policy changes
- Other operations deemed security-sensitive by the system

#### Scenario: Security policy is changed
- **WHEN** an authorized user changes a security policy
- **THEN** the system SHALL create an audit event with `category: security` and metadata containing the old and new policy values

#### Scenario: Automatic irrigation event occurs
- **WHEN** the automatic irrigation system triggers or stops irrigation
- **THEN** the system SHALL create an audit event with `actor.type: system`, `category: irrigation`, and metadata containing the trigger rationale and execution outcome

### Requirement: Audit event validation
The system SHALL validate audit event payloads before storing or rendering them.

- Audit events SHALL be validated for required fields (eventId, timestamp, actor, category, action, target, result).
- Invalid audit events SHALL be rejected and logged as security events.
- The frontend SHALL validate audit event payloads before rendering them.
- The backend SHALL validate audit event payloads before storing them.

#### Scenario: Invalid audit event is received
- **WHEN** the backend receives an audit event with missing required fields
- **THEN** the system SHALL reject the event and create a security audit event documenting the rejection

### Requirement: Audit event export
The system SHALL allow authorized users to export audit history.

- The export SHALL be available in CSV or JSON format.
- The export SHALL include all audit events matching the current filters.
- The export SHALL be restricted to authorized roles only.

#### Scenario: Admin exports audit history
- **WHEN** an authorized user exports the audit history
- **THEN** the system SHALL return a CSV or JSON file containing the filtered audit events
